==============================================================================
KYC MVP — Identity Verification API
Summary of implementation
==============================================================================

OBJECTIVE
---------
Server-side MVP identity verification pipeline focused on the core step:
  STEP_4_FACE_VERIFIED

The client uploads only raw files. All sensitive checks (OCR, face match,
expiry validation, scoring) are performed exclusively on the server.
No client-provided OCR results, face hashes, or match scores are trusted.


API ENDPOINTS
-------------

POST /kyc/identity-verification/init
  Auth: SCOPE_kyc:write
  Body: { referenceId, documentType, firstName, lastName, phoneNumber }
  Returns: { verificationId, status: "INITIATED" }

POST /kyc/identity-verification/{verificationId}/upload
  Auth: SCOPE_kyc:write
  Multipart: documentFront (required), documentBack (optional), selfie (required)
  Params: captureDevice, appVersion, platform (all optional)
  Returns: { verificationId, status: "PROCESSING" }
  Note: triggers async processing via RabbitMQ

GET /kyc/identity-verification/{verificationId}
  Auth: SCOPE_kyc:read
  Returns full result once processing is complete:
  {
    verificationId, status, currentStep,
    documentAnalysis: { documentReadable, documentExpired, documentType,
                        documentNumber (masked), fullName, dateOfBirth, expiryDate },
    faceMatch: { matched, score },
    reliabilityScore,
    scoreDetails: { documentReadability, ocrConfidence, documentValidity, faceMatch },
    decisionReason
  }

ADMIN ENDPOINTS (role ADMIN required)
--------------------------------------
GET  /admin/kyc/identity-verifications           — list all (optional ?status= filter)
GET  /admin/kyc/identity-verifications/{id}      — get full details (unmasked)
POST /admin/kyc/identity-verifications/{id}/review
  Body: { status: "APPROVED|REJECTED|REVIEW", reason: "..." }


PROCESSING PIPELINE (async via RabbitMQ)
-----------------------------------------
Queue: cpass.identity.verification.queue (configurable)

1. Download document front from S3
2. Run OCR via OcrService (StubOcrService in MVP)
   - Extracts: fullName, documentNumber, dateOfBirth, expiryDate, nationality, portraitBytes
3. Check document expiry
4. Download selfie from S3
5. Run face comparison via FaceMatchService (StubFaceMatchService in MVP)
   - Compares: document portrait vs selfie
   - Returns: matched (bool), score (0-100)
6. Compute reliability score via VerificationScoringService
7. Determine final status
8. Persist VerificationAnalysisEntity
9. Update IdentityVerificationEntity


SCORING ENGINE
--------------
Weighted sum formula (configurable, defaults sum to 100):

  Component            Weight   Raw Score Basis
  ---------------------------------------------------
  documentReadability    25     100 if readable, 40 if low-conf unreadable, 10 if unreadable
  ocrConfidence          20     OCR confidence value (0-100) from OcrService
  documentValidity       20     100 if valid, 50 if expiry unknown, 0 if expired
  faceMatch              35     Score (0-100) from FaceMatchService

  reliabilityScore = sum of weighted contributions

Decision thresholds (configurable):
  score >= 75 → APPROVED    (decisionReason: FACE_MATCH_OK_AND_DOCUMENT_VALID)
  score >= 50 → REVIEW      (decisionReason: LOW_CONFIDENCE_SCORE or FACE_MISMATCH)
  score <  50 → REJECTED    (decisionReason: INSUFFICIENT_RELIABILITY_SCORE)

Override rules (take precedence over score):
  document unreadable + confidence < 30 → REJECTED (DOCUMENT_UNREADABLE)
  document unreadable + confidence >= 30 → REVIEW   (DOCUMENT_UNREADABLE)
  document expired                       → REJECTED (DOCUMENT_EXPIRED)
  face score < faceMatchThreshold (75)   → REVIEW   (FACE_MISMATCH)

ERROR CODES
-----------
INVALID_FILE_FORMAT          — unsupported MIME type or missing required file
VERIFICATION_NOT_FOUND       — no verification for this client+ID combination
VERIFICATION_ALREADY_SUBMITTED — upload called twice on same verification
PROCESSING_FAILED            — S3 storage or broker error during upload
DOCUMENT_UNREADABLE          — OCR could not read the document
DOCUMENT_EXPIRED             — document expiry date is in the past
FACE_MISMATCH                — face match score below threshold
FACE_NOT_DETECTED            — face match service could not detect faces
INSUFFICIENT_RELIABILITY_SCORE — final score below minimum threshold
LOW_CONFIDENCE_SCORE         — score in review range (50–74)
FACE_MATCH_OK_AND_DOCUMENT_VALID — all checks passed (APPROVED)


STUB SERVICES — PRODUCTION REPLACEMENT PLAN
--------------------------------------------
StubOcrService (OcrService interface)
  → Replace with: AWS Textract, Google Cloud Vision, Azure Form Recognizer,
                  or an on-premise Tesseract/PaddleOCR integration.
  → The real implementation must extract: fullName, documentNumber, dateOfBirth,
    expiryDate, nationality, and the portrait face region from the document image.

StubFaceMatchService (FaceMatchService interface)
  → Replace with: AWS Rekognition CompareFaces, Azure Face API,
                  or an on-premise InsightFace/DeepFace model.
  → The real implementation must compare two face images and return a
    similarity score (0–100) and a matched boolean.

Neither stub reads or accepts client-provided values — this contract
must be preserved in all real implementations.


SECURITY NOTES
--------------
- Files are stored in S3/MinIO. Object keys include client_id prefix
  for logical isolation.
- Document numbers are masked in client-facing responses (AB**7890 format).
- Admin responses expose full unmasked data.
- File content is never logged — only size, MIME type, and object key.
- All endpoints enforce client isolation via JWT clientId claim.
- Cross-client access to verifications returns 404, not 403, to avoid
  enumeration of other clients' verification IDs.


STATUS FLOW
-----------
  INITIATED ──upload──► PROCESSING ──pipeline──► APPROVED
                                              └──► REVIEW
                                              └──► REJECTED

  Any status can be manually overridden by an admin via the review endpoint.
